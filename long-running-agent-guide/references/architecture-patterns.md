# 长时间运行 Agent 架构模式参考

本文档是 `long-running-agent-guide` Skill 的配套参考，详细说明每种核心架构模式的设计细节、实现思路和取舍分析。

---

## 1. 规划器/工作者/评判器（Planner/Worker/Reviewer）

### 设计哲学

这不是一个可选的风格偏好，而是长时间运行 Agent 的**结构性需求**。原因如下：

- **自我评估偏差**：模型在生成内容后倾向于认为自己的输出是正确的（确认偏误）
- **角色混淆**：同一上下文中既要"做事"又要"评判"，会导致评判标准逐渐被做事的便利性侵蚀
- **上下文污染**：工作过程中的大量细节会干扰评估的全局视角

### 三种实现层次

| 层次 | 实现方式 | 复杂度 | 隔离程度 | 适用场景 |
|------|---------|--------|---------|---------|
| L1 - Prompt 分离 | 同一模型，不同 System Prompt | 低 | 弱 | 简单任务，预算有限 |
| L2 - 会话分离 | 同一模型，独立会话（无共享上下文） | 中 | 中 | 中等复杂度任务 |
| L3 - 模型分离 | 不同模型（如 GPT-4 做规划，Claude 做执行） | 高 | 强 | 高可靠性需求 |

### L1 实现：Prompt 分离

```
规划器 System Prompt:
"你是一个任务规划专家。你的职责是将高级目标拆解为可执行的子任务。
 你不负责执行，只负责规划。每个子任务必须有：
 1. 明确的输入
 2. 明确的预期输出
 3. 验收标准
 4. 预估复杂度"

工作者 System Prompt:
"你是一个任务执行专家。你严格按照给定的子任务描述执行操作。
 你不能修改任务定义，不能跳过步骤。
 如果遇到阻塞，报告阻塞原因，不要自行决定替代方案。"

评判器 System Prompt:
"你是一个独立的质量评估专家。你只看结果和原始完成标准。
 你不关心实现过程中的困难或妥协。
 你的评判标准：
 1. 完成条件是否逐条满足？（是/否，不接受'部分满足'）
 2. 是否有副作用或遗留问题？
 3. 产出物质量是否达标？"
```

### L2 实现：会话分离（推荐的起步方案）

```
┌─ 规划会话 ─────────────────────────────────┐
│ 输入：原始目标 + 完成条件                     │
│ 输出：任务拆解列表 (JSON)                    │
│ 上下文：只包含目标信息，不包含实现细节         │
└──────────────────────────────────────────────┘
        │ 任务列表
        ↓
┌─ 工作会话 ─────────────────────────────────┐
│ 输入：单个子任务描述 + 工具访问权限            │
│ 输出：执行结果 + 产出物                       │
│ 上下文：只包含当前子任务的信息                 │
└──────────────────────────────────────────────┘
        │ 执行结果
        ↓
┌─ 评判会话 ─────────────────────────────────┐
│ 输入：原始完成条件 + 执行结果（不包含过程）    │
│ 输出：通过/不通过 + 具体反馈                  │
│ 上下文：只包含标准和结果，不包含"怎么做的"     │
└──────────────────────────────────────────────┘
```

## 2. 上下文重置（Context Reset）

### 为什么摘要不够

```
原始信息 (100% 保真度)
    ↓ 第一次摘要
摘要 1 (约 70% 保真度 — 丢失了细节和边界条件)
    ↓ 第二次摘要
摘要 2 (约 50% 保真度 — 丢失了关键决策的原因)
    ↓ 第三次摘要
摘要 3 (约 30% 保真度 — 只剩下"大概在做什么")
```

信息论角度：每次摘要都是有损压缩，且损失的不是均匀分布的——边界条件、例外情况、"为什么不选方案B"这类信息最先丢失，而这恰恰是长时间运行中最重要的信息。

### 上下文重置的实现流程

```
Step 1: 检测重置触发条件
├─ Token 使用达到窗口上限的 80%
├─ 经过了 N 轮对话（可配置，默认 50 轮）
├─ 完成了一个主要里程碑
└─ 评判器反馈显示对齐漂移

Step 2: 生成交接文件
├─ 从当前上下文中提取结构化信息
├─ 必须包含：原始完成条件（原文）、已完成工作、关键决策、下一步
├─ 交接文件是新会话的"入职文档"

Step 3: 销毁当前会话
├─ 保存事件日志到持久存储
├─ 清空上下文
└─ 不保留任何"隐式"状态

Step 4: 重建新会话
├─ 加载交接文件作为初始上下文
├─ 加载必要的 Memory Bank 条目
├─ 验证新会话理解了任务（让 Agent 复述目标和下一步）
└─ 继续执行
```

### 交接文件的关键设计原则

1. **完成条件原文复制** — 不做任何改写、摘要或"等价替换"
2. **决策只追加** — 决策记录是 Append-Only 的，新会话能看到完整决策链
3. **文件引用而非内容嵌入** — 大的产出物通过文件路径引用，不嵌入交接文件
4. **可验证** — 新会话启动后，让 Agent 复述目标和当前状态，人类或评判器验证

## 3. Memory Bank 设计模式

### 三层记忆架构

```
┌─────────────────────────────────────────────────────────────┐
│ 层 1: 工作记忆 (Working Memory)                               │
│ ├─ 位置：当前上下文窗口内                                      │
│ ├─ 生命周期：随会话存在                                        │
│ ├─ 内容：当前子任务的细节                                      │
│ └─ 操作：自动管理，无需显式读写                                 │
├─────────────────────────────────────────────────────────────┤
│ 层 2: 短期记忆 (Short-term Memory)                            │
│ ├─ 位置：交接文件 / 会话间传递的结构化数据                      │
│ ├─ 生命周期：跨会话，但限于当前任务                             │
│ ├─ 内容：进度、决策、阻塞项                                    │
│ └─ 操作：上下文重置时显式生成和加载                              │
├─────────────────────────────────────────────────────────────┤
│ 层 3: 长期记忆 (Long-term Memory)                             │
│ ├─ 位置：Memory Bank（文件系统/数据库/托管服务）                │
│ ├─ 生命周期：跨任务，持久存在                                   │
│ ├─ 内容：领域知识、历史经验、偏好设置                           │
│ └─ 操作：按需查询和写入，需要索引                               │
└─────────────────────────────────────────────────────────────┘
```

### Memory Bank 的文件系统实现（最简方案）

```
.agent/memory/
├── global/                    # 全局记忆（跨任务）
│   ├── preferences.md         # 用户偏好
│   ├── environment.md         # 环境信息
│   └── lessons-learned.md     # 经验教训（Append-Only）
│
├── tasks/                     # 任务级记忆
│   └── {task-id}/
│       ├── completion-criteria.md  # 完成条件（只读）
│       ├── handoff.md              # 最新交接文件
│       ├── decisions.md            # 决策记录（Append-Only）
│       ├── progress.md             # 进度追踪
│       └── events.jsonl            # 事件日志（Append-Only）
│
└── index.md                   # 记忆索引（自动维护）
```

### 读取优先级策略

```
每次会话启动或重置时：
P0 (必读): completion-criteria.md + handoff.md
P1 (当前): 当前任务目录下的所有文件
P2 (相关): 与当前任务相关的历史经验（从 lessons-learned.md 中按关键词匹配）
P3 (按需): 全局偏好和环境信息（仅在需要时加载）
```

## 4. Append-Only 事件日志

### 事件类型定义

| 事件类型 | 说明 | 关键字段 |
|---------|------|---------|
| `plan_created` | 规划器生成了任务拆解 | tasks[], priority |
| `task_started` | 工作者开始执行子任务 | task_id, expected_output |
| `tool_called` | 调用了工具 | tool_name, input, output, duration_ms |
| `tool_failed` | 工具调用失败 | tool_name, error, retry_count |
| `decision_made` | 做出了关键决策 | decision, reasoning, alternatives_considered |
| `checkpoint` | 保存了进度快照 | commit_hash, milestone, progress_pct |
| `review_result` | 评判器给出了评估 | pass/fail, feedback, criteria_checked |
| `context_reset` | 执行了上下文重置 | reason, token_usage, handoff_file_path |
| `alignment_check` | 执行了对齐检查 | drift_detected, original_goal_hash |
| `budget_warning` | 触发了预算告警 | current_spend, budget_limit, remaining_pct |

### JSONL 格式示例

```json
{"ts":"2025-05-15T09:30:00.000Z","type":"plan_created","role":"planner","ctx_id":"ctx-001","data":{"tasks":["设计API接口","实现核心逻辑","编写测试"],"priority":"task-1>task-2>task-3"}}
{"ts":"2025-05-15T09:30:05.000Z","type":"task_started","role":"worker","ctx_id":"ctx-001","data":{"task_id":"task-1","expected_output":"api.go 文件"}}
{"ts":"2025-05-15T09:31:00.000Z","type":"tool_called","role":"worker","ctx_id":"ctx-001","data":{"tool":"write_file","input":"api.go","duration_ms":150,"tokens":{"input":500,"output":1200},"cost_usd":0.0051}}
{"ts":"2025-05-15T10:00:00.000Z","type":"context_reset","role":"system","ctx_id":"ctx-001","data":{"reason":"token_limit_80pct","token_usage":95000,"handoff":"tasks/task-001/handoff.md","new_ctx_id":"ctx-002"}}
```

## 5. 成本控制模式

### 预算守卫的分层策略

```
Layer 1 — 软限制（预警）
├─ 消耗达到预算的 50% → 记录日志
├─ 消耗达到预算的 70% → 发送告警
└─ 消耗达到预算的 90% → 切换到低成本模式（如使用更小的模型）

Layer 2 — 硬限制（断路）
├─ 消耗达到预算的 100% → 暂停所有 API 调用
├─ 生成当前状态的交接文件
└─ 通知人类决定是否追加预算

Layer 3 — 异常检测（智能断路）
├─ 连续 5 次相同工具调用 → 可能陷入循环 → 暂停
├─ 单次工具调用成本 > 历史平均值的 10 倍 → 暂停
└─ 10 分钟内无有效进度产出 → 触发对齐检查
```

### 成本优化技巧

1. **分级模型策略**：规划用强模型（准确性重要），执行用弱模型（速度重要），评判用中等模型
2. **缓存工具输出**：相同输入的工具调用结果缓存，避免重复调用
3. **批量处理**：将多个小的独立任务合并为一次调用
4. **提前终止**：评判器在发现方向性错误时立即终止，不等到所有子任务完成

## 6. 与分布式系统经典模式的对照

| Agent 概念 | 分布式系统对照 | 核心思想 |
|-----------|---------------|---------|
| 上下文重置 | Checkpoint & Recovery | 定期保存状态，故障后从最近检查点恢复 |
| 事件日志 | Event Sourcing | 通过重放事件重建任何时刻的状态 |
| 规划器/工作者 | CQRS | 读写分离，查询和命令走不同路径 |
| Memory Bank | 分布式缓存 + 数据库 | 热数据在缓存（上下文），冷数据在数据库（持久存储） |
| 对齐检查 | 心跳检测 + 健康检查 | 定期验证系统是否在正确状态 |
| 预算断路器 | Circuit Breaker | 错误率/成本超阈值时断开，防止级联失败 |
| 多 Agent 协调 | 分布式事务 (Saga) | 通过补偿操作实现最终一致性 |
| 完成条件文件 | SLA/SLO | 可量化的服务等级目标 |
| 工具调用幂等性 | 幂等性设计 | 相同请求重复执行结果一致 |
| Agent 对齐漂移 | 拜占庭容错 | 系统中的节点可能表现异常 |
