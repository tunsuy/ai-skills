# 长时间运行 Agent 架构设计指南

> 聊天窗口和可以通宵干活的 Agent 之间的差距，关键不在模型，而在包裹它的那层状态管理、会话记录和交接机制。

本 Skill 将「如何构建长时间运行 Agent」这一问题拆解为可操作的架构决策和工程实践，帮助你根据具体场景选择正确的路径。

## When to Use

**触发条件：**

- 当用户要构建运行时间超过单次对话窗口的 Agent
- 当用户面临 Agent 上下文溢出、目标漂移、成本失控等问题
- 当用户需要设计 Agent 的状态持久化、会话管理或错误恢复机制
- 当用户要搭建多 Agent 协调系统
- 当用户在评估 Agent 运行时平台（Google Agent Platform / Claude Managed Agents / 自建方案）

**不适用场景：**

- 简单的单轮问答或短对话场景
- 无需状态持久化的一次性脚本任务
- 纯模型调优或 prompt engineering（不涉及运行时架构）

## Prerequisites

### 知识要求

- 理解 LLM 上下文窗口的概念和限制
- 基本的分布式系统概念（状态管理、事件日志、幂等性）
- 了解至少一种 Agent 框架（Claude Code、Cursor、ADK、LangGraph 等）

### 技术栈参考

| 场景 | 推荐技术栈 | 备选方案 |
|------|-----------|---------|
| 开发者编码 Agent | Claude Code / Cursor + Git Worktree | Codex / Antigravity |
| 托管 Agent 产品 | Google Agent Platform / Claude Managed Agents | ADK + 自托管 |
| 自主运维 Agent | ADK + Memory Bank + Cloud Run + Scheduler | LangGraph + Redis + K8s CronJob |

## Quick Reference

| 核心概念 | 一句话解释 |
|----------|-----------|
| 规划器/工作者/评判器 | 将规划、执行、评估分离到不同角色，防止自我打分 |
| 上下文重置 | 拆除当前会话，从结构化交接文件重建新会话（类比新员工入职） |
| Memory Bank | 可查询的持久化记忆服务，跨会话保持状态 |
| 完成条件文件 | Agent 启动前写好的外部文件，含可测试的完成标准 |
| Append-only 事件日志 | 只增不改的会话日志，使 Agent 可恢复、可调试、可审计 |
| Ralph 循环 | Agent 声称完成但你不信时，反复要求验证的机制 |
| 大脑/双手分离 | 模型推理和代码执行在不同权限域中运行 |

## Procedure

### Step 1: 场景定位 — 你在构建什么？

在开始任何架构设计之前，先明确你属于以下哪种场景：

```
┌────────────────────────────────────────────────────────────────────────┐
│                        场景决策树                                       │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│  Q1: 你是 Agent 的使用者还是构建者？                                     │
│      │                                                                 │
│      ├─ 使用者 → 场景 A：开发者编码 Agent                                │
│      │          （用现成工具，专注 AGENTS.md 和钩子）                      │
│      │                                                                 │
│      └─ 构建者 → Q2: Agent 的执行环境？                                  │
│                  │                                                      │
│                  ├─ 面向用户的产品 → 场景 B：托管 Agent 产品              │
│                  │                  （选托管运行时，专注业务循环）          │
│                  │                                                      │
│                  └─ 自动化/监控/运维 → 场景 C：自主运维 Agent             │
│                                       （Memory Bank + 定时调度）         │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

**每种场景的关键行动：**

| 场景 | 核心关注点 | 第一步行动 |
|------|-----------|-----------|
| A - 开发者编码 | AGENTS.md + 钩子 + worktree | 写好 AGENTS.md，加类型检查和 lint 钩子 |
| B - 托管产品 | 选运行时 + 业务循环设计 | 评估 3 个托管方案，选一个先跑起来 |
| C - 自主运维 | Memory Bank + 调度 + 告警 | 搭建 ADK + Memory Bank + 调度器基础设施 |

### Step 2: 启动前的检查清单 — 投入产出比最高的单一举措

**无论哪种场景，都必须在 Agent 启动前完成这件事：写下完成条件。**

创建一个 `completion-criteria.md` 文件（或任何你喜欢的名字），包含：

```markdown
# 任务完成条件

## 目标
[一句话描述任务最终要达到的状态]

## 完成标准（可验证的）
- [ ] [Given-When-Then 格式的标准 1]
- [ ] [Given-When-Then 格式的标准 2]
- [ ] [Given-When-Then 格式的标准 3]

## 反面案例（不应该做什么）
- ❌ [不应该发生的行为 1]
- ❌ [不应该发生的行为 2]

## 超时与兜底
- 最大运行时间：[X 小时]
- 如果超时：[具体的降级策略]
- 如果失败：[回退到什么状态]

## 进度检查点
- [ ] [里程碑 1] — 预期在 [时间] 完成
- [ ] [里程碑 2] — 预期在 [时间] 完成
```

**为什么这是投入产出比最高的举措？**

- 防止 Agent 在运行中途偷偷重新定义"完成"
- 给评判器提供客观标准
- 使人类审计变得可能
- 本质上就是写一份好的需求规格说明

### Step 3: 核心架构模式 — 规划器/工作者/评判器分离

```
┌───────────────────────────────────────────────────────────────┐
│                  三角色分离架构                                  │
│                                                               │
│   ┌──────────┐     任务拆解      ┌──────────┐                 │
│   │  规划器   │ ───────────────→ │  工作者   │                 │
│   │ Planner  │                   │ Worker   │                 │
│   │          │ ← 进度报告 ────── │          │                 │
│   └────┬─────┘                   └────┬─────┘                 │
│        │                              │                        │
│        │ 完成条件                      │ 工作产出                │
│        ↓                              ↓                        │
│   ┌──────────┐                                                │
│   │  评判器   │ ← 独立评估，不受工作者的"自我感觉良好"影响       │
│   │ Reviewer │                                                │
│   └──────────┘                                                │
│        │                                                       │
│        ├─ 通过 → 提交结果                                      │
│        └─ 不通过 → 反馈给规划器，重新规划                        │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

**关键原则：**

1. **自我打分是失败模式** — 让写代码的人做自己的 Code Review 永远不靠谱
2. **哪怕用同一个模型，角色不同、prompt 不同就够了** — 关键是视角分离
3. **评判器的 prompt 只包含完成条件，不包含实现细节** — 防止被工作者的思路带偏

**类比 Clean Architecture：**

| Agent 角色 | Clean Architecture 层 | 职责 |
|-----------|----------------------|------|
| 规划器 | UseCase 层 | 定义"做什么"，任务拆解和优先级排序 |
| 工作者 | Repository/Infrastructure 层 | 执行"怎么做"，调用工具完成具体操作 |
| 评判器 | 独立的 Validation Service | 判断"做对没"，只看结果不看过程 |

### Step 4: 上下文管理策略

长时间运行的最大技术挑战是上下文窗口的有限性。

```
┌─────────────────────────────────────────────────────────────────────┐
│                  上下文管理策略阶梯                                    │
│                                                                     │
│  Level 1: In-Context 摘要（简单但有损）                               │
│  ├─ 方法：在上下文内对历史对话做摘要                                   │
│  ├─ 问题：摘要再摘要 → 信息保真度递降                                  │
│  └─ 适用：< 2 小时的任务                                             │
│                                                                     │
│  Level 2: 上下文重置 + 交接文件（推荐）                                │
│  ├─ 方法：拆除当前会话，从结构化交接文件重建新会话                       │
│  ├─ 类比：让新工程师入职 — 给文档，不给口头总结                         │
│  ├─ 交接文件包含：目标、进度、关键决策、当前阻塞、下一步                 │
│  └─ 适用：2-24 小时的任务                                            │
│                                                                     │
│  Level 3: Memory Bank 持久化（最完整）                                │
│  ├─ 方法：可查询的外部记忆服务，Agent 按需读写                         │
│  ├─ 实现：文件系统 / Redis / 向量数据库 / 托管服务                     │
│  ├─ 关键：记忆需要索引，不能只是 dump                                  │
│  └─ 适用：> 24 小时或跨天/跨周的持续任务                               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 上下文重置的交接文件模板

```markdown
# Agent 交接文件

## 上下文摘要
[当前任务的一段话概述]

## 原始目标（从 completion-criteria.md 复制，不要改写）
[保持原始完成条件的原文，防止对齐漂移]

## 已完成的工作
- [x] [已完成项 1] — 产出物：[文件/PR/提交]
- [x] [已完成项 2] — 产出物：[文件/PR/提交]

## 当前进度
- 总体进度：[X/Y] 个里程碑已完成
- 当前正在进行：[具体任务描述]
- 阻塞项：[如果有]

## 关键决策记录（Append-Only）
1. [时间] 决策：[内容] — 原因：[为什么]
2. [时间] 决策：[内容] — 原因：[为什么]

## 下一步行动
1. [优先级最高的下一步]
2. [第二步]
3. [第三步]

## 需要注意的陷阱
- ⚠️ [已知的坑 1]
- ⚠️ [已知的坑 2]
```

### Step 5: 会话日志设计 — Append-Only 事件日志

**核心原则：如果你不能从持久存储重建 Agent 在过去 24 小时做了什么，你拥有的只是一个碰巧调用 LLM 的长时间运行 shell 脚本。**

```
┌─────────────────────────────────────────────────────────────┐
│                  事件日志结构                                  │
│                                                             │
│  每条事件包含：                                               │
│  ├─ timestamp: 精确到毫秒的时间戳                             │
│  ├─ event_type: plan | action | tool_call | result |        │
│  │              error | decision | checkpoint | handoff      │
│  ├─ agent_role: planner | worker | reviewer                 │
│  ├─ content: 事件内容                                        │
│  ├─ context_window_id: 当前上下文窗口的 ID                    │
│  ├─ token_usage: 本次调用的 token 消耗                       │
│  └─ cost_usd: 本次调用的成本                                 │
│                                                             │
│  关键要求：                                                   │
│  ✅ Append-Only — 只追加，不修改，不删除                       │
│  ✅ 结构化 — JSON/Protobuf，不要纯文本                        │
│  ✅ 可查询 — 按时间范围、事件类型、角色筛选                     │
│  ✅ 可导出 — 方便做后续分析和审计                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Step 6: 成本控制 — 断路器和预算守卫

**没有预算守卫的长时间运行 Agent = 开着水龙头睡觉。**

```
┌─────────────────────────────────────────────────────────────┐
│                  成本控制三道防线                               │
│                                                             │
│  第一道：预算硬上限                                           │
│  ├─ 设定单次运行的美元上限                                    │
│  ├─ 到达上限 → 暂停并通知人类                                 │
│  └─ 实现：每次 API 调用后累加成本，到阈值断路                   │
│                                                             │
│  第二道：工具调用限速                                          │
│  ├─ 单次循环内的工具调用次数上限                               │
│  ├─ 防止 Agent 陷入无限循环                                   │
│  └─ 实现：Rate Limiter（令牌桶/滑动窗口）                      │
│                                                             │
│  第三道：异常检测                                              │
│  ├─ 连续 N 次相同工具调用 → 可能陷入循环                       │
│  ├─ token 消耗突然飙升 → 可能在做无用功                        │
│  ├─ 错误率超过阈值 → 可能走错方向                              │
│  └─ 实现：滑动窗口统计 + 阈值告警                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Go 实现思路（伪代码）：**

```go
// BudgetGuard 是预算守卫，保护 Agent 不会无限烧钱
type BudgetGuard struct {
    maxBudgetUSD    float64
    currentSpendUSD float64
    maxToolCalls    int
    currentCalls    int
    mu              sync.Mutex
}

// Check 在每次 API 调用前检查是否超预算
func (bg *BudgetGuard) Check() error {
    bg.mu.Lock()
    defer bg.mu.Unlock()

    if bg.currentSpendUSD >= bg.maxBudgetUSD {
        return fmt.Errorf("budget exceeded: spent $%.2f of $%.2f limit",
            bg.currentSpendUSD, bg.maxBudgetUSD)
    }
    if bg.currentCalls >= bg.maxToolCalls {
        return fmt.Errorf("tool call limit reached: %d of %d",
            bg.currentCalls, bg.maxToolCalls)
    }
    return nil
}
```

### Step 7: 安全架构 — 大脑/双手分离

```
┌─────────────────────────────────────────────────────────────┐
│              大脑/双手分离模型                                  │
│                                                             │
│  ┌─────────────────┐     ┌─────────────────┐               │
│  │   大脑 (Brain)   │     │   双手 (Hands)   │               │
│  │                 │     │                  │               │
│  │ • LLM 推理      │     │ • 代码执行        │               │
│  │ • 计划生成       │ ──→ │ • 文件操作        │               │
│  │ • 工具选择       │     │ • API 调用        │               │

│  关键安全边界：                                               │
│  ✅ 模型不能直接访问凭据（通过 Secret Manager 间接引用）        │

│  ✅ 网络访问有白名单限制                                       │
│  ✅ 文件系统操作限定在工作目录内                                │
│  ✅ 所有操作有审计日志                                         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Step 8: 对齐漂移防护 — 钩子和评判者

**对齐漂移是长时间运行 Agent 最阴险的故障模式。**

原始目标被总结 → 再总结 → 再总结 → 失去保真度。

```
┌─────────────────────────────────────────────────────────────┐
│               对齐漂移防护策略                                  │
│                                                             │
│  1. 完成条件文件永远不被摘要                                   │
│     └─ 每次上下文重置，原文复制完成条件，不做任何改写            │
│                                                             │
│  2. 定期对齐检查（每 N 个工具调用或每 M 分钟）                  │
│     └─ 评判器角色："当前工作方向是否仍然服务于原始目标？"         │
│                                                             │
│  3. 钩子机制（类型检查 / lint / 测试）                          │
│     └─ 将失败结果反馈给 Agent，形成自动纠偏循环                 │
│                                                             │
│  4. Ralph 循环（Agent 声称完成时）                              │
│     └─ 不信？让 Agent 用具体证据证明每个完成标准都已满足         │
│                                                             │
│  5. 进度提交（每个有意义的工作单元）                             │
│     └─ Git commit / 文件快照 / 状态保存                        │
│     └─ 使回退成为可能，不会因漂移丢失全部进度                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Step 10: 场景专项指南

#### 场景 A：开发者编码 Agent

```
实操清单：
1. ✅ 写 AGENTS.md — 当作飞行员检查清单，每一条都是踩过坑才写进去的
2. ✅ 添加钩子 — 类型检查（go vet）、lint（golangci-lint）、测试（go test）
3. ✅ 将钩子失败反馈给 Agent — 让 Agent 看到错误并自行修复
4. ✅ 启动前写计划文件 — 明确目标、步骤、完成标准
5. ✅ 使用 Ralph 循环 — Agent 说完成了？用完成条件逐条验证
6. ✅ 多小时任务用 worktree — 合笔记本不杀进程
7. ✅ 每个工作单元提交 — git commit 保存进度
```

#### 场景 B：托管 Agent 产品

```
决策矩阵：

                    开箱即用  自定义程度  模型灵活性  成本
```

## Pitfalls

### ⚠️ 陷阱 1：摘要压缩导致信息丢失

**症状：** Agent 在长时间运行后"忘记"了早期的关键决策或约束条件。

**原因：** 通过摘要压缩上下文时，细节逐级丢失。摘要的摘要的摘要 ≈ 信息蒸馏到无意义。

**解决方案：** 使用上下文重置而非摘要压缩。完成条件文件永远原文复制，不做任何改写。关键决策记录使用 Append-Only 日志，独立于上下文存在。

### ⚠️ 陷阱 2：Agent 偷偷重新定义"完成"

**症状：** Agent 声称任务完成，但实际上跳过了困难的部分或降低了标准。

**原因：** 没有外部的、不可变的完成条件文件。Agent 在上下文中"合理化"了自己的跳过行为。

**解决方案：** 完成条件写在外部文件中，Agent 不能修改。评判器用原始完成条件逐条检查，不接受"等效替代"。

### ⚠️ 陷阱 3：无限循环烧钱

**症状：** 一觉醒来，API 账单飙到天花板。

**原因：** Agent 陷入了"尝试 → 失败 → 换个方式尝试 → 失败"的循环，没有断路器。

**解决方案：** 三道防线——预算硬上限、工具调用限速、异常检测。任何一道触发都暂停并通知人类。

### ⚠️ 陷阱 4：沙箱权限过大

**症状：** Agent 意外修改了不该碰的文件、访问了不该访问的 API、暴露了凭据。

**原因：** 大脑和双手在同一个权限域运行，没有隔离。

**解决方案：** 严格的大脑/双手分离。模型推理过程无权访问凭据。代码执行在沙箱中，文件系统和网络有白名单限制。

### ⚠️ 陷阱 5：多 Agent 状态冲突

**症状：** 多个 Agent 在同一个代码库上工作，产生冲突提交、覆盖对方的改动。

**原因：** 缺少分布式锁或协调机制。

**解决方案：** 每个 Agent 使用独立的 Git 分支或 worktree。通过 Agent 间消息传递（而非共享文件系统）协调。使用乐观锁 + 冲突检测 + 自动 merge（类似分布式系统的 Saga 模式）。

### ⚠️ 陷阱 6：写出的规格说明不够具体

**症状：** Agent 做出了合理但不符合预期的行为，因为规格说明有歧义。

**原因：** 人类习惯了"我知道我什么意思"，但 Agent 不知道。

**解决方案：** 用 Given-When-Then 格式写规格。包含反面案例。让另一个人（或另一个 Agent）读你的规格说明，检查是否有歧义。

## Verification

### 架构自检清单

- [ ] 已明确场景类型（A/B/C）
- [ ] 有外部的、不可变的完成条件文件
- [ ] 规划/执行/评估三个角色已分离（至少 prompt 层面的分离）
- [ ] 上下文管理策略已选定（摘要/重置/Memory Bank）
- [ ] 有 Append-Only 的事件日志
- [ ] 有成本控制三道防线（预算/限速/异常检测）
- [ ] 代码执行在沙箱中，与模型推理隔离
- [ ] 对齐漂移有防护机制（定期检查 + 钩子反馈）
- [ ] 每个工作单元有进度提交（commit/快照）
- [ ] 有可观测性方案（产出物 + 日志 + 度量 + 告警）

### 运行验证

```
运行 Agent 前：
✅ completion-criteria.md 已写好

✅ 预算上限已设置

运行中检查（每小时/每个里程碑）：
✅ 成本在预算范围内
✅ 工具调用无异常循环
✅ 对齐检查通过
✅ 有新的 commit/进度

运行结束后：
✅ 所有完成标准逐条验证通过
✅ 事件日志可查询、可重建完整执行轨迹
✅ 成本报告生成
✅ 经验教训记录（更新 AGENTS.md）
```

## Advanced Usage

### 多 Agent 协调模式

```
┌─────────────────────────────────────────────────────────────┐
│            多 Agent 协调：从分布式系统借鉴的模式                │
│                                                             │
│  模式 1: 主从模式（Master-Worker）                            │
│  ├─ 一个规划 Agent 分配任务给多个工作 Agent                    │
│  ├─ 适用：可明确拆分的并行任务                                │
│  └─ 风险：主节点瓶颈                                          │
│                                                             │
│  模式 2: 流水线模式（Pipeline）                                │
│  ├─ Agent A 的输出是 Agent B 的输入                           │
│  ├─ 适用：有明确前后依赖的任务                                │
│  └─ 风险：下游等待上游，整体延迟高                             │
│                                                             │
│  模式 3: 事件驱动模式（Event-Driven）                          │
│  ├─ Agent 通过事件总线通信，无直接依赖                         │
│  ├─ 适用：松耦合的自主运维场景                                │
│  └─ 风险：事件风暴、因果关系难追踪                             │
│                                                             │
│  模式 4: 共识模式（Consensus）                                 │
│  ├─ 多个 Agent 独立完成同一任务，通过投票选出最佳结果           │
│  ├─ 适用：高可靠性要求的决策场景                               │
│  └─ 风险：成本 N 倍增长                                       │
│                                                             │
│  所有模式共有的需求：                                          │
│  • 唯一的任务 ID + 分布式追踪                                  │
│  • 幂等性保证（同一任务重复执行不产生副作用）                   │
│  • 死锁检测和超时回退                                          │
│  • 共享状态的并发控制（乐观锁/CAS）                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Agent 自我修复与运行框架进化

```
当前的前沿问题（尚无标准答案）：

1. Agent 能否读取自己的运行轨迹并修补自己的运行框架？
   → 初步可行：通过分析事件日志中的失败模式，自动更新 AGENTS.md

2. 运行框架能否为任务即时组装工具和上下文？
   → 方向：动态工具发现 + 按需加载（类似微服务的服务发现）

3. 多个长时间运行 Agent 如何避免共享代码库上的冲突？
   → 借鉴：Git worktree + 分支隔离 + Merge Bot
   → 更远：分布式事务 Saga 模式在 Agent 编排中的应用
```
